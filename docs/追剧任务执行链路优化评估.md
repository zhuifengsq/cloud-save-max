# 追剧任务执行链路优化评估

> 评估对象：`backend/app/infrastructure/execution/`（DramaTaskExecutor 及其协作者）、`backend/app/infrastructure/drive/`（网关 / 转存策略 / 夸克适配器）、`backend/app/infrastructure/scheduling/task_scheduler.py`
> v1 评估方式：静态阅读（逐行核对调用点与请求次数）+ 既有文档交叉比对；**原评估未运行测试或实测网络耗时**
> 评估日期：2026-11-23
> 版本：v2。以下先记录当前实现，原始评估及其中的代码行号保留为 v1 快照。

## 当前实现

- **夸克转存断点**记录发起的批次、网盘任务 ID 和已取得的文件 ID。每批使用 120 秒轮询预算。续跑优先使用已知文件 ID 核对目标目录，否则继续查询原任务。查询失败保留断点和原因。提交结果不明且缺少任务 ID 和文件 ID 时，由用户核对网盘后处理。
- **整包目录逐文件续跑**通过 `fallback_dirs` 记录。只有能核实为完整的分享列表才会增加 `fallback_missing` 缺失次数。默认连续缺失 3 次后暂缓，可通过 `DRAMA_FALLBACK_MISSING_LIMIT` 调整。目录重新出现时清零，并在当轮补齐文件。仅同名的普通文件不会解除目录暂停。
- **目录范围变更**在断点只有目录续跑记录且能核实其他配置一致时生效。纳入白名单或选中目录后，旧断点仍按精确文件名补齐，成功后才清理。检测到分享子目录列表不完整时会保留断点。排除规则命中的目录单独暂缓，其他目录继续执行。旧断点在首次按原配置执行时补记用于核实范围变更的信息。
- **恢复操作**位于「追剧任务 → 编辑 → 转存断点」。可单独放弃某个目录的续跑记录，已转存文件及其他断点会保留。放弃后，已有同名目标目录可能被整包跳过，缺集可能需要手工补齐。因任务配置或有效重命名规则变化而阻塞的断点，会在恢复匹配配置后的下一次执行中继续。
- **目标目录必须能唯一确定**。目录列表中的重名或缺少 ID、按路径查得的目标不匹配或指向文件，都会阻止向该目标写入。目录深度通过 `DRAMA_SYNC_MAX_DEPTH` 配置，默认 6 层。截断会列出未处理路径，并阻止「运行一次」提前把任务禁用。
- **普通模式重命名**等各批转存确认后统一执行。首次校验全部通过时省掉第二次读目录。校验读取失败会保留待确认状态。大目录每批用于关联文件的翻页成本仍需用真实网盘测量。

## 一、结论摘要

这条链路的功能是完整的，问题分三类：

1. **可靠性（P0）**：夸克 `query_task` 是无界轮询，配合调度器「单线程顺序执行 + `max_instances=1`」，一次卡死会让**所有**追剧任务永久停摆；另有「目录深度 > 3 静默丢弃」导致少转存且任务仍报 success。
2. **网络放大（P1）**：每个子目录重复解析自己已存在的 fid（3~5 次请求可以压到 2 次）；每次批转存都要把整个目标目录重新全量翻页；重命名要两次全量翻页，且首次翻页失败会把全部重命名重放一遍。
3. **整洁度（P2）**：多处死代码、未用 import、列表线性查名、大小写敏感的目录匹配、两套重复的「根目录文件转存计划」实现。

| 编号 | 级别 | 位置 | 问题 | 影响 |
| --- | --- | --- | --- | --- |
| P0-1 | P0 | `quark_adapter.py:352-381` | `query_task` 无超时、无最大次数，`status==3` 继续轮询 | 单条转存可永久挂起，拖死整轮调度 |
| P0-2 | P0 | `drama_executor.py:705-707` | `depth > 3` 静默 `return []` | 深层剧集永不转存，任务仍报 success |
| P1-3 | P1 | `drama_executor.py:153-176,690-718` | 每个子目录重复 `get_fids`；父 listing 的目录 fid 被丢弃；`mkdir` 后多一次 `get_fids` | 每目录 3~5 次请求，可降到 2 次 |
| P1-4 | P1 | `transfer.py:112-123` + `quark_adapter.py:277-315` | 每 100 个一批，每批都全量 `ls_dir(destination)` | 大库存时是主导网络成本 |
| P1-5 | P1 | `drama_executor.py:343-396` | 重命名两次全量 listing；首次 listing 失败 → 全部重命名重放 | 每次任务多 N/50 次请求，限流时成倍放大 |
| P2-6 | P2 | `drama_plan.py:112-140` | `dest_filename_list` 是 list，逐个线性查找 | 微优化，改 set |
| P2-7 | P2 | `drama_executor.py:494,790` | `dest_dir_map` 原始大小写 key | 大小写不同的同名目录被重复整包转存 |
| P2-8 | P2 | 见 §四 | 死代码 / 未用 import / 重复实现 | 维护成本、规则漂移 |

## 三、P0：可靠性

### P0-1 夸克 `query_task` 无界轮询

**证据** `backend/app/infrastructure/drive/adapters/quark_adapter.py:352-381`

```python
retry_index = 0
while True:
    response = self._send_request("GET", url, params=querystring).json()
    if response["status"] != 200:
        logger.warning('Quark task status query failed')
        return response
    if response["data"]["status"] == 2:
        break
    else:
        if retry_index == 0:
            pass
        retry_index += 1
        time.sleep(0.500)
```

只有 `data.status == 2` 会退出。`status == 3`（失败）也继续每 0.5s 轮询一次，**无最大次数、无总超时**。

**影响链**

- `transfer.py:97-99` 只在 `query_task` **抛异常**时降级成 `pending`；这里永不抛，所以永远不降级。
- `task_scheduler.py:209-257` 是单线程 `for task_id in task_ids`，job 注册为 `max_instances=1`（`:121/:146/:172/:198`）。一个任务卡住 → 本轮后续任务全部不执行，下一轮 cron 因 `max_instances=1` 直接跳过。
- 进程不退出、没有错误日志、执行记录一直停在 running 态。

**改法**（超时 → pending，失败态 → failed）

```python
class QuarkAdapter(BaseCloudDriveAdapter):
    QUERY_TASK_TIMEOUT_SECONDS = 120      # 类常量，避免适配器依赖 settings

    def query_task(self, task_id: str) -> Dict:
        import time
        from datetime import datetime
        retry_index = 0
        deadline = time.monotonic() + float(self.QUERY_TASK_TIMEOUT_SECONDS)
        response: Dict = {}
        while True:
            # ... 原 querystring / _send_request 不变 ...
            response = self._send_request("GET", url, params=querystring).json()
            if response.get("status") != 200:
                logger.warning("Quark task status query failed")
                return response
            data = response.get("data") or {}
            if data.get("status") == 2:
                return response
            if data.get("status") == 3:
                # 失败态不能继续转；transfer.py:103-104 已有同样判断，这里提前收敛
                return {"code": 1, "status": 200, "message": "转存任务失败", "data": data}
            if time.monotonic() >= deadline:
                logger.warning("Quark task query timeout task_id=%s", task_id)
                return response          # data.status != 2 → transfer 判 pending（待确认）
            retry_index += 1
            time.sleep(min(0.5 + 0.1 * retry_index, 3.0))
```

为什么超时返回「原响应」而不是失败：`transfer.py:105-106` 对 `status not in (2, None)` 返回 `pending`，执行器把它记成 skipped（`drama_executor.py:249-250` 的 `SkipTask`），下一轮 cron 再试。慢但最终成功的转存不该被标成 failed；而失败态（3）有明确语义，可以直接报错。

**验收**

- 假适配器：轮询 20 次仍 `status==1` → 在 `QUERY_TASK_TIMEOUT_SECONDS` 后返回 pending，任务状态 `skipped`；
- `status==3` → 立刻返回，任务状态 `failed`，`run_log` 里出现失败原因；
- 现有 `tests/test_quark_task_share.py` 全绿（该文件已覆盖正常转存路径）。

**配套（可选，防御纵深）**：调度器加「单任务墙钟上限」——每任务开始记时间，循环内检查 `now - started > N` 时记 warning 并进入下一个任务。注意它只能让调度器往前走，**不能真正终止**已卡住的线程，所以根因仍要修 `query_task`。

### P0-2 深层目录静默丢弃

**证据** `drama_executor.py:705-707`

```python
if depth > 3:
    self._line(f"层级过深，跳过: {rel_label}")

```

增量路径与 `copy_all` 退化路径都走这里。分享里套了 4 层以上时，剧集永远不会被转存，但 `execute()` 正常返回、任务记 success。

## 四、P1：网络放大

### P1-3 每个子目录重复解析已存在的 fid

**证据**

- `drama_executor.py:153-163`：`_ensure_dest_dir_fid` = `_try_get_dir_fid`（`:144`，`get_fids([path])`）→ 无则 `_mkdir` → 再来一次 `_try_get_dir_fid`；
- `drama_executor.py:710`：`_sync_share_dir_incremental` 对**每个**子目录无条件调 `_ensure_dest_dir_fid(dest_path)`，父级 fid 明明已知（还作为 `dest_base_fid` 传进函数，但函数体从未使用）；
- `drama_executor.py:165-176`：`_list_dest_names` 遍历时对目录项直接 `continue`，把 `name→fid` 丢了；`:203-214` 的 `_list_dest_dir_map` 又单独列一次同样的目录。

**改法**

1. `_list_dest_names` 与 `_list_dest_dir_map` 合并为 `_list_dest_children(dest_fid, ignore_extension) -> tuple[set[str], dict[str, str]]`，一次 listing 同时产出「文件名集合」和「目录名→fid」；
2. 递归新增参数 `dest_fid: str | None`：已知就直接用，未知才走 `_ensure_dest_dir_fid`；子目录 fid 从父 listing 的 `dir_map` 取；
3. `_ensure_dest_dir_fid` 改用 `mkdir` 返回的 `data.fid`，省掉建目录后的第二次 `get_fids`；
4. 删掉从未使用的 `dest_base_fid` 参数，避免误导。

```python
def _ensure_dest_dir_fid(self, savepath: str) -> str:
    existing = self._try_get_dir_fid(savepath)
    if existing:
        return existing
    response = self._mkdir(savepath)
    created = str(((response or {}).get("data") or {}).get("fid") or "")
    if created:
        return created
    created = self._try_get_dir_fid(savepath)   # 兜底：个别网盘 mkdir 不回 fid
    if created:
        return created
    raise RuntimeError("创建目录失败")
```

`copy_all=True` 的路径目前**不列**目标目录（`:718` 的 `if not copy_all else set()`），改完之后要保持这个短路，否则退化路径会多出一次 listing。

**验收**：假适配器统计调用次数——已存在目录 2 次（`get_detail` + `ls_dir`），新建目录 3 次（`mkdir` + `get_detail` + `ls_dir`）；`tests/test_folder_diff_mode.py` 全绿。

### P1-4 每批转存都要全量翻目标目录

**证据** `transfer.py:112-123`：`associate` 之前必调 `saved_listing` → `adapter.ls_dir(destination)`；`quark_adapter.py:277-315` 默认 `max_items=0`、`_size=50` 全量分页。而 `drama_executor.py:244-245` 每 100 个一批，于是**每一批**都要把目标目录从头翻到尾，只为建立「名字 → 新 fid」映射。

按 `_size=50` 推算：目标目录 2000 个文件 = 40 页，每批 40 次请求；转 300 集（3 批）= 120 次请求，这还没算 `save_file` / `query_task`。

**两个方向**

- **批大小**：先确认夸克 `sharepage/save` 单次 `fid_list` 上限（社区实现常见 100），若可放大到 200~300，批数直接减半以上，listing 次数同比减少。改动最小、风险最低。
- **位置映射**：`cloud115_adapter.py:470/551`（注释明确「按 file_names 顺序排列」）、`cloud189_adapter.py:2246`（`aligned`）、`cloud139_adapter.py:803`（`aligned_fids`）说明多家适配器本就保证 `save_as_top_fids` 与请求顺序一致。可以给 `TransferStrategy` 加 `ids_aligned = False` 类属性，在「数量相等 + ids 唯一 + 本批无重名」时按位置映射，否则回退到 listing + 名字匹配。

**风险与前置**：位置映射一旦错位，重命名会作用到别的文件，属于「静默错数据」。夸克是否保序**无法从本仓库代码证明**，必须先做比对实验：临时在 `associate` 里对同一批同时按位置和按名字映射，把不一致的批次打 warning，跑若干真实任务观察一段时间，再决定是否开启。

**验收**：`ids_aligned=True` 的适配器路径下不再调用 `ls_dir(destination)`；回退条件（重名/数量不符/ids 有重复）有单测覆盖。

### P1-5 重命名两次全量 listing（且失败会整体重放）

**证据** `drama_executor.py:343-396`

- `:345` 第一次 `_ls_dir(dest_root_fid)` 求 `need_retry`；
- `:379` 重试后再 `_ls_dir(dest_root_fid)` 一次算最终 `final_ok/final_failed`；
- `:354-356` 第一次 listing 抛异常时 `fid_name = {}` → `:359-363` 把**全部** `attempted` 判成 `need_retry` → N 次 rename 原样再打一遍（限流场景下最糟，正好是应该收手的时候）。

**改法**

1. `need_retry` 为空时跳过第二次 listing，用第一次的 `fid_name` + `failed` 集合算出 `final_ok/final_failed`；
2. 第一次 listing 失败时把状态标成「未知」，**不重试**（rename 本身已有 `_retry` 三层），只记警告并按 `attempted - failed` 估计；
3. 只有真正发生重试时才做第二次 listing（此时校验才有增量价值）。

**验收**：全部重命名成功的任务只 `ls_dir` 一次；`_ls_dir` 抛错的任务不产生额外 `rename` 调用。
